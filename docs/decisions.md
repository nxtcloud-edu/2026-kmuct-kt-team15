## 전제

- **기준 자료:** 아키텍처 그림 4장(`kirothon/docs/diagrams`, 9/18), 상민의 UI 시안(`UI (1).html`, 최신), `kirothon/docs/에이전트_아니어도_되는_일.md`.
- **기능은 UI를 최대한 따른다.** UI를 바꾸는 것은 그림의 데모 장면이 UI 없이 안 될 때뿐이다. UI에 보이는 기능은 백엔드까지 실제로 구현한다.
- **개발 도구:** 4명 모두 Claude Code. Kiro는 쓰지 않는다.
- **인프라:** 주최측이 주는 EC2(Ubuntu)와 S3. 포트는 1개로 안다.
- **LLM:** 외부 API를 써도 된다(주최측 확인). llm-x 게이트웨이를 쓴다. 게이트웨이 특성은 `kirothon/core/llm.py` 주석에 있다.
- **사전 준비 규칙:** 코드는 미리 가져갈 수 없다. 문서, 프롬프트, DB는 가져갈 수 있다. 제출용 repo는 당일 주최측이 따로 만든다.
- **구현 범위 (그림 기준):**
  - 구현: 수집기, 스케줄러, 공지 해석 에이전트, 공지 연결, 검토 대기열, kmu.db, 판정 엔진, 학생 정보, 웹 화면, 질의 에이전트(19번, 순서는 마지막)
  - 설계만: 수집 설정 생성 에이전트, 성적 화면 읽기

## 데이터와 판정

**1. 데모 기준일은 2026-03-16으로 가정한다.**
크롤 데이터는 2026-02-01 ~ 04-30 공지라 실제 오늘 날짜로 거르면 목록이 빈다. 게시가 가장 많은 주는 개강 직후인 3/2 주(93건)와 3/9 주(90건)다. 해석이 끝나 마감일을 알게 되면 모집 중 공지가 가장 많은 날로 다시 정한다. 서버 설정 `DEMO_TODAY` 하나로 둔다.

**2. 판정 화면은 UI 그대로, 백엔드는 상태를 4개로 구분한다.**
- 화면: 목록은 "지원할 수 있는 공지"와 "조건이 안 맞는 공지" 두 갈래. 조건 행은 ✓ / ✗ / 확인 필요.
- 백엔드: 해당, 비해당, 정보 부족, 확인 중. 되묻기는 정보 부족을, 검토 대기열은 확인 중을 쓰기 때문에 구분한다. 화면에서는 둘 다 "확인 필요"로 보인다.
- 충돌 배지는 두지 않는다. 배제·중복 조건(245건, 26%)은 일반 조건 행으로 다룬다. 예: "타 장학 수혜 이력"이 프로필에 없으면 확인 필요가 되고 되묻기 대상이 된다.

**3. 분야는 UI 그대로 두 목록을 쓴다.**
필터는 5종(장학, 인턴·현장실습, 국제교류, 교내활동, 학사·전공), 관심 분야는 8종(5종 + 창업, 공모전·경진대회, 자격증·어학). 공지 카드의 분야 값은 8종 중 하나다. 추가 3종 공지는 필터를 고르지 않았을 때만 목록에 보인다.

**4. 관심 분야는 저장만 한다.**
정렬은 UI 규칙대로 NEW 먼저, 그다음 마감순이다.

**5. 학과 분류표는 UI의 단과대별 학과 목록을 쓴다.**
소속 조건이 있는 공지는 309건(33%)이다. "SW 관련 학과" 같은 조건은 학생 학과와 바로 비교할 수 없으므로, 해석 에이전트가 공지당 한 번 이 표를 보고 학과 목록으로 바꿔 저장한다. 판정은 포함 여부만 본다(판정 LLM 0회 유지). 목록 출처가 나무위키라 공식 편제와 대조해야 한다.

**6. 어학 성적은 학생당 시험 1개(UI 그대로), IELTS를 추가한다.**
조건은 여러 시험 중 하나를 충족하면 통과한다(UI의 `reqMap` 방식). 본문에 어학 시험이 나오는 공지 9건 중 8건이 여러 시험 중 하나를 요구한다. 교환학생 공지가 IELTS를 요구하는데 UI 선택지에 없어서 추가한다.

**7. 로그인 없이 브라우저마다 익명 학생을 둔다.**
참여자와 심사위원이 데모를 직접 쓸 수 있으므로, 브라우저마다 익명 `student_id`를 localStorage에 두고 첫 방문 때 온보딩부터 시작한다. 두 학생 장면은 UI의 "처음부터 보기"나 내 정보 수정으로 보여준다. DB에는 학생 몇 명을 미리 넣어 두어 운영자 보정 때 "학생 N명 재판정"을 보여준다.

## 흐름

**8. 온보딩은 UI 그대로 둔다 (학점과 어학 포함).**
온보딩 밖의 항목으로도 되묻기가 돈다: 직전 학기와 누적 학점의 구분(성적 조건 212건), 소득 분위(30건), 수혜·참여 이력(배제·중복 245건), 이수 학점, 입학 연도.

**9. 되묻기는 홈 목록 위의 질문 카드 1개로 한다. (UI 추가, 상민에게 요청)**
그림의 데모 장면 "질문 하나에 답하면 보류된 공지가 한꺼번에 정리된다"에 필요하다. UI의 "오늘 할 일" 카드와 선택지 칩을 재사용한다. 백엔드는 보류된 공지를 가장 많이 푸는 항목을 고르고, 선택지 경계값을 보류된 공지들의 조건에서 뽑고, 답을 받으면 한꺼번에 다시 판정한다.

**10. "원문 보기" 시트는 원문 저장본을 보여준다. (시트 내용 변경, 상민에게 요청)**
에이전트가 실제로 읽은 원문 저장본(본문, 첨부 변환 텍스트, 이미지 판독 텍스트)을 출처별 구역으로 나눠 보여주고, 구역마다 출처 링크를 붙이고, 조건으로 인용한 문장을 강조한다. "홈페이지에서 보기" 버튼은 지금처럼 공지 URL로 간다. 에이전트가 조건을 어디서 찾았는지를 화면에 보여주는 곳이 여기다.

**11. 확인 중 표시는 UI 그대로 둔다.**
조건 행의 "확인 필요"와 부족분 문구를 쓴다.

**12. 운영자 화면은 학생 화면과 따로 `/admin` 한 장으로 만든다.**
검토 대기열 목록, 원문 보기, 조건 값 입력, 저장하면 다시 판정하고 "학생 N명 재판정"을 보여준다. 공지 숨김 스위치를 둔다(점검에서 틀린 공지를 숨길 때 쓴다). `.env`의 비밀번호로 막는 것을 권장한다.

**13. "새 공지 확인"은 UI 흐름 그대로, 백엔드는 데모 모드로 돈다.**
진행 표시, NEW, 알림은 UI 그대로. 버튼을 누르면 미리 빼 둔 공지 1건을 새 공지로 넣고 해석 에이전트를 실제로 돌린다. 해석 과정은 10번의 원문 시트에서 보여준다. 실제 사이트를 지금 수집하면 9월 공지가 들어와 3/16 기준 데모와 어긋나기 때문이다. UI 문구 "12곳"은 "30곳"으로 바꾼다. 발표 직전에 돌릴 초기화 명령을 둔다(누가 먼저 누르면 발표 때 새 공지가 없기 때문이다).

**14. 공지 연결은 백엔드만 구현한다.**
여러 게시판에 올라온 같은 공지를 목록에서 하나로 합친다. 제목이 같은 것만 세도 20묶음 51건이다. 화면에 따로 표시하지 않는다.

## 계획과 알림

**15. 계획 기능은 UI 그대로 구현한다.**
계획에 넣기와 빼기(지원 불가면 버튼 비활성), 할 일 체크, 주간 달력, 홈의 오늘 할 일. `plan`, `task` 테이블과 API를 둔다.

**16. 할 일은 해석 에이전트가 뽑고, 날짜는 규칙으로 계산한다.**
해석 에이전트가 공지 카드에 "준비할 일"을 뽑는다(따로 뽑으면 같은 공지를 두 번 읽는다). 날짜는 마감에서 서류별 준비 기간을 빼서 정한다. 준비 기간 표(10종 정도)는 팀이 쓴다. 할 일 틀은 공지당 하나, 완료 여부는 학생별로 저장한다. 제출 서류 조건이 있는 공지는 237건(25%)이다.

**17. "캘린더 앱에 모두 추가"는 목업으로 둔다.**
지금처럼 토스트만 띄운다.

**18. 알림은 화면 안 배너로, 내용은 백엔드가 계산한다.**
새 공지가 학생 조건에 맞을 때, 계획에 넣은 공지 마감 3일 전과 그날 할 일. 실제 푸시와 메일은 보내지 않는다.

## 대화

**19. 질의 에이전트를 구현한다. 순서는 맨 마지막이다.**
UI의 메인 탭이고 그림의 두 번째 에이전트다. 카드와 판정 엔진을 조회해서 답하므로 둘이 먼저 있어야 한다. 도구는 공지 검색, 내 정보, 자격 판정(판정 엔진 호출, LLM 0회), 내 계획, 내 정보 수정(21번). 첨부는 해석 때 카드에 들어가 있으므로 대화에서 첨부를 읽지 않는다. UI의 추천 질문 6개는 시안의 가짜 공지 기준이라 실제 데이터 기준으로 바꾼다.

**20. 가정 질문은 자격 판정 도구의 옵션으로 넣는다.**
"학점 3.2여도 돼?"는 가정 값을 넣어 판정 엔진을 한 번 더 부른다.

**21. 되묻기 답과 학생 정보는 대화 탭에서 고친다.**
질의 에이전트에 "내 정보 수정" 도구를 넣는다. 저장 전에 "학점을 3.8로 바꿀까요?"처럼 확인을 받고, 저장하면 다시 판정한다. 19번을 못 하게 되면 이 수정 경로도 없어진다.

## 외부 사용자 대비

참여자와 심사위원이 데모를 직접 쓸 수 있다. 구현 완성도보다 이것이 깨지지 않는 게 중요하다.

**꼭 할 것**
1. 브라우저마다 익명 학생을 따로 둔다 (7번).
2. 새 공지 데모 초기화 명령을 둔다 (13번).
3. 대화의 LLM 동시 실행 수를 제한하고(예: 3), 세션마다 분당 질문 수를 제한하고, 시간 초과 때 "잠시 후 다시" 안내를 띄운다.
4. 대화 입력을 300자로 제한한다. 게이트웨이는 긴 user 메시지에 토큰을 끼워 넣고 32k를 넘으면 조용히 자른다. 대화에서 답을 못 한 질문은 검토 대기열과 따로 쌓는다.
5. 목록에는 해석이 끝나고 점검한 공지만 보인다. 점검은 상세 화면의 조건과 마감을 원문 시트와 대조해 맞음/틀림을 표시하는 것이다. 한 건에 1분 정도이고 4명이 나눈다. 틀린 공지는 `/admin`에서 고치거나 숨긴다. 이 결과는 발표의 정확도 수치(예: 30건 중 27건)로 쓴다.
6. FastAPI 앱 하나가 화면, API, `/admin`을 한 포트로 서빙한다. 화면은 API를 `/api/...` 상대 경로로 부른다. llm-x 키는 서버 `.env`에만 두고, S3는 비공개로 둔다.

**권장**
- `/admin` 비밀번호 (12번).
- 데모 기준일 표시: 내 정보 화면의 기존 안내 문구 날짜를 바꾼다.
- SQLite WAL 모드.
- 실명과 학번은 받지 않는다. 학번이 필요한 조건은 입학 연도로 묻는다.
- 접속 주소 QR을 발표 슬라이드에 넣는다.

LLM이 멈춰도 목록, 상세, 판정은 동작한다. 멈추는 것은 대화 탭과 새 공지 해석뿐이다.
